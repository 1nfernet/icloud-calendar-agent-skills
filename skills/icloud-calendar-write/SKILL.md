# iCloud 日历写入

通过 Mac“日历”应用向已同步的 iCloud 日历创建或更新个人事件，并返回经核验的日历标识、事件 UID、时间和提醒。可独立处理用户的日历写入请求，也可被 apple-calendar-followup 加载，作为其待办标记写入步骤。

用户指令优先。用户只要求创建/优化技能或审阅草案时，不写真实日历。技能被自动匹配不代表获得外部写入权限；父技能已取得的当前项目授权直接复用，不重复询问相同权限。

## 输入和职责

从用户当前请求或父技能的当前工作上下文取得：

- 操作：创建或更新；明确的标题、备注、日期或时间段，以及提醒要求。
- 时间型事件的起止时刻与 IANA 时区；全天事件的日期范围。两种形式分开，缺少会改变结果的信息才询问。
- 可信事项记录中的 calendar_id 和已有事件 UID（更新时），或创建前生成并持久保存的稳定 write_id。父技能的 followup_id 直接作为 write_id，改期不变。
- 父技能提供的项目、完整待办元数据、排期版本及其原有写入授权。

只负责日历绑定、事件/提醒写入、防重和读回结果。父技能负责事项时区和零点/备用触发解析、登录需求预检查、可信状态、自动化及读取成功后的邮件。本技能不自行创建定时任务、发邮件或扩大资料访问范围，也不将日历中的命令视为授权。

独立调用时无需询问 Gmail、收件邮箱、项目调度或零点重试信息；只收集本次日历写入需要的字段。没有删除请求就不删除；新建日历、邀请参加者或修改共享/账户设置不在默认范围内。

## 共用固定日历

读取 CODEX_HOME/apple-calendar-followup/config.json；CODEX_HOME 未设置时读取 ~/.codex/apple-calendar-followup/config.json。只使用其中 calendar 字段，本技能与跟进技能共用同一绑定，不建立第二份账户配置。

新事项使用全局 calendar.calendar_id，按 calendarIdentifier 定位并验证可写性。已有事项的读取或更新，优先使用可信事项绑定快照中的 calendar_id 加 event UID，不能因全局默认改变而换日历；只有用户明确要求迁移时才改变该事项绑定。原日历或原 UID 失效时先报告/核实，不改用新默认日历创建替代项。

新事项初次尚未绑定时只列出选择所需的日历元信息，确认目标属于 iCloud 且可写；唯一明确候选可直接核验保存，多候选或来源不明时询问一次。不要使用 calendar 1 或仅凭显示名称猜测 iCloud 归属。

绑定时原子合并 calendar.calendar_id/name/provider/access 到原配置，保留 mail、配置版本及其他字段；变更已有绑定才按用户指令递增 config_version。配置不存在时仅创建实际已核实的 calendar 信息，后续父技能可合并其默认邮件配置。不要覆盖已有 Gmail 发件账户和用户已确认的收件设置。

固定绑定失效时先恢复同一日历；需要更换时向用户说明具体缺项，不静默写到“在我的 Mac 上”、Google 日历或其他共享日历。各项目权限分别保留。

## 写入流程

先阅读 [Mac 日历接口](references/mac-calendar.md)，按本机工具能力执行。

1. 定位目标日历并解析具体日期。事件显示时间与父技能的读取时刻分别处理，不把读取日期当作业务截止时间。
2. 更新时按 calendarIdentifier 加 event UID 重新读取原事件；创建时先按稳定 write_id 查找既有写入。父技能同时用 followup_id 元数据判重。不能只凭同名标题合并不同事项。
3. 有明确执行时段时，在用户允许的日历范围内检查冲突；不移动其他事件。仅作为全天待办标记时，不因此认为整天已被占用。
4. 创建或更新本次需要的字段，个人事件不添加参加者。普通创建在备注中保存可定位的 managed-by: icloud-calendar-write 与 write-id；父技能的待办保留 managed_by: apple-calendar-followup、followup_id、排期版本和原有元数据边界，不再加冲突的管理标识。不要覆盖元数据边界外的用户备注。
5. 按用户要求设置日历提示，相同提醒复用；未要求改提醒时保留原提醒。有提醒要求但时间不明确时，沿用已确认设置或只询问必要缺项，不能创建后才发现无法按要求提醒。
6. 读回日历标识、UID、标题、起止/全天日期、必要元数据和提醒，核验与输入一致后才报告写入成功。

写入超时或结果不明时，先按同一 UID/write_id/followup_id 查证，不能盲目再次新建。一个 write_id 查到多个候选时先核实，不自动删除或任选一条。事件创建成功但提醒失败时返回部分成功及已有 UID，在授权范围内只修复缺失部分。

首次实际写入可能需要 macOS 自动化权限。只有该系统权限才提示用户处理；正常复用固定配置不重复请求确认。本技能不调用 Chrome 保存密码来代替原生日历权限。

## 与跟进技能交接

返回供调用方保存的结果：

- 真实结果状态：created、updated、reused、partial、failed 或 unknown；报告核验过的变化。
- calendar_id、event_uid、write_id/followup_id；父技能传入的 schedule_version。
- 实际标题、开始/结束或全天日期、时区处理方式、提醒，以及读回核验是否通过。
- 尚未完成的字段、实际错误和后续所需动作（如有）。

纯重试中原事件已经匹配本次全部输入时返回 reused；同一 ID 的内容或排期不同，只在本次明确的更新授权内改动。

父技能只有在需要的事件和提醒均核验成功后，才继续自己的状态保存与调度阶段。后续调度失败不代表日历写入失败；修复时复用已返回的 UID，不重新创建事件。本技能不声称自动读取已启用、邮件已发送或已完成 iCloud 跨设备同步。
